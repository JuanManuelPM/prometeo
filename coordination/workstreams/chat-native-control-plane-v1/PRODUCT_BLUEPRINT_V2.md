# Prometeo Reencarnable Chat + Parallel Worker System v2

Status: PRODUCT NORTH STAR + IMPLEMENTATION BLUEPRINT
Owner workstream: `chat-native-control-plane-v1`

## 0. Product in one sentence

Prometeo turns a long-lived piece of work into a **durable Chat Object** that can be reincarnated into any fresh ChatGPT conversation, while disposable one-shot worker chats execute pre-published jobs in parallel and write their progress/results back to durable state so the main Chat Object can keep coordinating without the human transporting context.

A ChatGPT conversation is an **execution shell**, not the memory, identity, plan or authority of the work.

---

# 1. Human experience

## 1.1 Fresh Home

The human opens a new ChatGPT conversation and sends only:

`Prometeo`

Prometeo loads the durable selector and shows the available durable Chat Objects / projects, for example:

1. Facultad
2. Alumnos
3. Prometeo · continuidad entre chats

The human sends only the number. The number is immediately resolved to a durable identity. The conversation then says, in effect, **"you are now this Chat Object"** and reconstructs its current operating state.

The menu number is not identity and may change. Durable identity is explicit.

## 1.2 Reincarnation

At any moment the current conversation may be abandoned. A new conversation can select the same durable Chat Object and continue from the exact durable frontier.

Reincarnation must reconstruct at least:
- identity and role;
- core mission and human goal;
- current objectives;
- current frontier;
- settled design decisions;
- invariants / things that must not be broken;
- negative knowledge / failed directions;
- current architecture map;
- shared components and owners it depends on;
- active work items and delegated workers;
- completed returns not yet consumed;
- unresolved questions;
- relevant recent durable changes;
- pointers for deeper archaeology only if required.

The fresh conversation must not require the previous transcript to operate correctly.

## 1.3 Natural work

Once reincarnated, the human talks normally. The Chat Object continuously maintains its durable self-description while designing and building:
- ideas become indexed;
- decisions become explicit;
- rejected ideas become negative knowledge when useful;
- architecture changes update the design map;
- new work is added to a queue;
- dependencies/shared elements are recorded;
- material results update the frontier;
- unresolved questions remain visible.

The durable object is not a transcript summary. It is the **current executable model of the work**.

## 1.4 Parallel delegation

The main Chat Object can decide that some work should be parallelized. It creates the jobs **before** the worker chats exist.

Example:
- J01 audit current architecture;
- J02 build a candidate schema;
- J03 inspect existing Supabase owners;
- J04 adversarially review regression risks;
- J05 prototype the compiler change.

Each job is persisted with all required context and an exact return contract.

The human then opens several fresh chats and pastes only tiny launch commands such as:

`Prometeo J01`

or an opaque short launch code/URL generated by Prometeo.

No long prompt is transported by the human.

## 1.5 Worker lifecycle visible to the main Chat Object

A worker is a disposable conversation, normally one mission and one return.

Its durable lifecycle is observable:

`PREPARED → CLAIMED → STARTED → WORKING → RETURNED → DONE`

Exceptional terminal states:

`BOUNDARY | FAILED | CANCELLED | SUPERSEDED`

The main Chat Object can therefore truthfully synthesize states such as:
- 5 jobs prepared;
- 5 workers started;
- 3 returned;
- 2 still working;
- all 5 returned, integration/review can begin.

This is derived from durable run state, not guessed from conversation memory.

## 1.6 Integration

Workers do not directly become truth merely because they finished.

Returns are inputs to the parent Chat Object / Steward. The parent:
1. reads all relevant returns;
2. detects conflicts/overlap;
3. compares them to Current, rules and preserved behavior;
4. merges useful findings or artifacts;
5. records accepted/rejected/superseded outputs;
6. advances its own frontier;
7. optionally spawns a second parallel round.

One authoritative integrator/steward must control canonical promotion when multiple workers produce overlapping candidates.

# 2. Core object model

## 2.1 Durable Chat Object

A **Chat Object** is the durable representation of one long-lived working conversation/persona/project seat.

It has a stable `chat_object_id` and contains/pointers to:

### IDENTITY
- `chat_object_id`;
- `project_id`;
- title / human label;
- role;
- owning workstream(s);
- creation/lineage;
- current incarnation metadata if any.

### MISSION
- why this object exists;
- human goal;
- definition of success;
- non-goals.

### FOCUS
- current frontier;
- active objectives;
- next decisions/actions;
- current blockers;
- open questions.

### DESIGN BOARD
- architecture map;
- current product model;
- design principles;
- decisions and rationale;
- hypotheses/candidates clearly separated from accepted facts;
- experiments;
- future ideas.

### RULES / NEGATIVE KNOWLEDGE
- invariants;
- must-preserve behavior;
- known regressions;
- failed approaches;
- prevention rules;
- do-not-repeat list.

### SHARED GRAPH
- shared components/capabilities consumed;
- canonical owners;
- dependencies;
- adapters/overrides;
- branches/child workstreams;
- impact relationships.

### WORK BOARD
- prepared work items;
- active delegated runs;
- worker states;
- completed returns awaiting consumption;
- integrated/rejected/superseded returns.

### EVIDENCE / LINEAGE
- important commits/files/packets/returns;
- current authoritative refs;
- relevant historical source pointers;
- optional references to ChatGPT conversations when available.

Chat history is supplemental evidence/archaeology. It is never the only durable representation.

## 2.2 Project vs Chat Object vs Workstream vs Worker

These identities must not be collapsed:

- `project_id`: human-level umbrella, e.g. Alumnos.
- `chat_object_id`: durable conversational/operational seat that can reincarnate.
- `workstream_id`: durable execution stream / coordination scope.
- `work_item_id`: one delegated unit of work.
- `worker_instance_id`: one disposable execution chat/agent instance.
- ChatGPT conversation/thread id: optional platform evidence when exposed; never required for correctness.

A project can contain multiple Chat Objects. A Chat Object can coordinate multiple workstreams and many work items. A work item may have one or more worker runs if retried/challenged.

# 3. Reincarnation protocol

When a fresh conversation selects a Chat Object:

1. **BOOT** — load stable Prometeo entry/runtime.
2. **RESOLVE** — menu/code → `chat_object_id`.
3. **IDENTITY** — load Chat Object manifest.
4. **FRESHNESS** — read EPOCH / relevant compiled state.
5. **SELF** — load mission, FOCUS, rules, design board and work board.
6. **SHARED** — resolve current owners/dependencies/shared elements relevant to the frontier.
7. **WORKERS** — derive active/returned worker runs and unconsumed returns.
8. **RECENT DELTA** — load relevant changes since last incarnation.
9. **ARCHAEOLOGY OPTIONAL** — search prior ChatGPT conversations/history only if durable state cannot resolve a contradiction or useful missing detail.
10. **BIND** — create/bind this conversation's disposable incarnation/worker identity to the durable Chat Object.
11. **CONTINUE** — resume from durable frontier.

This is `REINCARNATE`, not transcript replay.

---

# 4. Self-documenting main Chat Object

The main Chat Object has an obligation to maintain itself.

After material design/thinking/execution changes, it updates durable state before the conversation becomes the only place where the idea exists.

Material updates include:
- new goal or objective;
- architecture decision;
- changed assumption;
- newly discovered existing capability;
- new invariant;
- regression/failure lesson;
- new work item;
- worker spawn plan;
- return consumed;
- dependency or owner change;
- frontier completion/shift.

The rule is **conversation → distilled durable state**, not conversation → transcript archive.

Raw transcript may be recoverable from ChatGPT and may be referenced when useful, but the product cannot depend on rereading it all.

# 5. Delegated one-shot worker model

## 5.1 Job exists before chat

A delegated worker must boot from a durable `JOB`/Execution Packet already prepared by the parent.

Minimum job contents:
- work_item_id;
- parent `chat_object_id`;
- parent/workstream ids;
- exact mission;
- why it matters;
- baseline/current refs;
- smallest sufficient context;
- must-preserve map;
- allowed write scope;
- forbidden scope;
- dependencies;
- expected artifact/answer;
- verification requirements;
- return path/contract;
- completion/boundary conditions.

The worker launch message is only an address to this job.

## 5.2 Worker boot

A fresh chat receives `Prometeo <job-code>`.

It:
1. resolves the job;
2. loads stable runtime/constitution;
3. validates job freshness and owner state;
4. creates its own independent worker run/status object;
5. writes `STARTED` before substantive execution;
6. loads only the job's relevant context;
7. executes through implementation/critique/repair where authorized;
8. writes a durable RETURN/evidence receipt;
9. marks its run `DONE` or a real terminal boundary;
10. disappears safely.

The human should not need to send a second message to make a well-formed worker finish.

## 5.3 Worker independence

Workers may run concurrently when scopes do not collide. They must not all mutate a shared central status file.

Each worker/run writes its own state. Parent/control views are derived.

## 5.4 Worker outputs

A return distinguishes:
- observations/facts;
- candidate decisions;
- changed artifacts;
- tests/evidence;
- conflicts;
- unresolved boundaries;
- suggested parent actions.

A worker cannot self-promote its candidate to Human Accepted/Current/Served unless the relevant authority explicitly allows that operation.

# 6. Parent orchestration / Control Room behavior

The parent Chat Object periodically derives a small control summary before/while doing its own work.

It tracks:
- number of prepared jobs;
- active runs;
- started time / last material update;
- return availability;
- failed/boundary jobs;
- collisions;
- dependencies now satisfied;
- unconsumed returns;
- whether a batch is sufficiently complete to integrate.

Important: there is no requirement to interrupt every reply with noisy status. The parent should surface worker state when it changes the next useful action.

Example behavior:
- Parent keeps designing while 5 workers run.
- After a user message it notices 3 returns; it can continue the current discussion while noting 2 are still active if relevant.
- When the fifth returns, PRE_RESPONSE/control refresh notices the batch is complete and the parent can say integration/review is now ready.

This is event/state awareness, not a conversational Inbox metaphor.

# 7. Existing Prometeo pieces to reuse

## 7.1 Agent Network v3
Reuse:
- independent worker status objects;
- derived read-only Network;
- EPOCH freshness;
- convergence/collision events;
- NEEDS / PROVIDES / DEPENDS_ON / IMPACTS;
- no-global-lock model;
- public/private boundary.

Extend it to understand `chat_object_id`, `work_item_id`, batch/run relationships and richer worker lifecycle.

## 7.2 Work Packets / Execution Packets
Reuse them as the worker's pre-published job/context carrier.

The existing execution contract already encodes a critical principle: worker recovery/execution must not depend on chat identity. Preserve that.

## 7.3 RETURN
Reuse as durable result/evidence, but make parent consumption state explicit:
- RETURNED;
- CONSUMED;
- INTEGRATED;
- REJECTED;
- SUPERSEDED.

## 7.4 EPOCH
Reuse as cheap shared freshness. Do not force every parent/worker to scan the entire system on each turn.

## 7.5 Current / Catalog / Lineage / shared runtime
Reuse existing authority. The Chat Object coordinates and remembers; it does not become product authority merely by documenting something.

## 7.6 Historical worker/export patterns
Preserve the useful old pattern:

`Planner/Compiler → prebuilt jobs → N disposable workers → durable returns → validator/reconciler → single Steward/Merger → next state`

The new Chat Object architecture makes that pattern native to ChatGPT rather than requiring large copied prompts/ZIPs.

---

# 8. What Inbox/Outbox becomes

Directed messaging is still useful but **secondary**.

Use a message/event only when a worker needs to communicate something outside normal job/run/return state, e.g.:
- request information from another active owner;
- signal a collision/blocker;
- notify a dependency change;
- ask a targeted question;
- deliver an urgent correction before normal return.

Normal orchestration should flow through:

`Chat Object state → Work Item → Worker Run → Return → Parent consumption`

not through a stream of chat messages.

# 9. Idea index

## Objectives

### O01 — Conversation erasure tolerance
Any main conversation can vanish without losing the product state or plan.

### O02 — One-command reincarnation
A fresh chat needs only `Prometeo` + a short selection/code to become the correct durable Chat Object.

### O03 — Self-documenting intelligence
Important reasoning becomes structured durable state while work proceeds.

### O04 — Parallel scale
The main Chat Object can prepare many independent jobs and continue useful work while disposable workers execute them.

### O05 — Zero human context courier
The human copies only tiny selectors/launch codes, never full context or worker returns.

### O06 — Observable delegation
The parent knows which workers are prepared, started, working, returned and done from durable evidence.

### O07 — Safe convergence
Parallel worker output is reconciled through explicit authority/integration instead of accidental last-writer-wins.

### O08 — Preserve accumulated intelligence
Rules, failures, design rationale and shared capability ownership survive model/chat replacement.

## Architecture ideas

### A01 — Durable Chat Object manifest
One canonical manifest represents the chat and points to its living subdocuments/state.

### A02 — Design Board
A durable evolving map of architecture, decisions, experiments, rules and pending ideas.

### A03 — Work Board
Prepared jobs + worker runs + returns + consumption/integration state.

### A04 — Reincarnation
Fresh shell reconstructs Chat Object and becomes its current incarnation.

### A05 — One-shot workers
New chat + tiny code → claim prepared job → execute → durable return → terminal state.

### A06 — Derived Control Room
Parent status is compiled from independent run/return objects, not manually maintained prose.

### A07 — Batch orchestration
A parent can prepare 1..N jobs, observe partial return, and automatically recognize batch completion.

### A08 — Steward/Merger
One canonical integration authority reconciles overlapping candidates.

### A09 — Progressive retrieval
Chat Object loads compact self-state first and deep history only when required.

### A10 — ChatGPT history as auxiliary memory
When available, prior conversations may be searched to recover nuance/evidence, but durable state remains sufficient for operation.

## Problems being solved

### P01
Long conversations end or become unusable and critical context is trapped inside them.

### P02
A fresh chat does not know what it is, what was decided or what not to break.

### P03
Parallel workers historically required long prompt/context transport by the human.

### P04
Parent chats cannot reliably know whether external workers actually started/finished.

### P05
Good design insights remain conversational prose and get rediscovered/repeated.

### P06
Workers can duplicate existing shared capabilities because they do not resolve owners first.

### P07
Parallel outputs can collide or diverge without a canonical reconciliation mechanism.

### P08
`latest commit`/`worker says done` can be confused with Current/Human Accepted/Served.

## New conclusions in this iteration

### N01
The primary abstraction is **Chat Object**, not Mailbox.

### N02
`Inbox` is optional event transport; ordinary worker feedback belongs to durable job/run/return state.

### N03
A Chat Object needs a durable Design Board and Work Board in addition to FOCUS.

### N04
Worker jobs are **precompiled before the worker chat exists**; the launch text is only an address.

### N05
Worker lifecycle must be richer and queryable so the parent can know partial/full batch completion.

### N06
`project_id` alone is too coarse; add `chat_object_id` so one project can eventually contain multiple durable conversational seats.

### N07
The main Chat Object should continue doing useful work while child jobs execute; coordination is ambient, not a blocking mode.

### N08
The system should exploit itself to build itself: this workstream can generate several small prepared jobs for audits/schema/runtime/compiler/testing and use disposable chats to execute them in parallel.

# 10. Fastest implementation path

## Phase A — Make the current main chat a real Chat Object
1. Define `prometeo.chat-object/v1`.
2. Create this workstream's durable Chat Object manifest.
3. Attach FOCUS, Design Board, rules, shared graph and work board pointers.
4. Change Home selection from project-only binding to Chat Object binding.
5. Define reincarnation read order.

## Phase B — Make delegation real without private messaging
1. Define Work Item and Worker Run contracts.
2. Add `work-items/<id>/JOB.json` structure.
3. Add independent `runs/<worker-id>.json` status.
4. Reuse RETURN for result.
5. Add tiny worker launch resolver.
6. Add parent batch summary compiler.

This gives most of the desired product without waiting for a mailbox backend.

## Phase C — Use Prometeo to build Prometeo
Prepare 5–10 narrow jobs from this blueprint, for example:
- existing runtime/compiler audit;
- Chat Object schema review;
- Work Item/Run schema implementation;
- launch resolver implementation;
- batch summary compiler;
- adversarial architecture review;
- tests/fresh-chat reincarnation harness.

Run them in disposable fresh chats using only short job codes.

## Phase D — Reconcile and integrate
Parent consumes returns, resolves conflicts, updates the Chat Object, and launches the next batch if useful.

## Phase E — Add targeted messaging only where state/returns are insufficient
Implement a small directed event/question channel after actual use proves the gap.

# 11. Acceptance tests

The product is real when all are true:

1. Fresh chat: `Prometeo` → Home.
2. Select an item → it resolves to a durable `chat_object_id`.
3. Fresh chat reconstructs mission/design/rules/frontier/work board without old transcript.
4. Main Chat Object can prepare at least 5 durable independent jobs.
5. Five fresh worker chats can each launch using only a tiny code.
6. Every worker marks durable STARTED before material work.
7. Parent can correctly report partial completion (e.g. 3/5 returned) from durable state.
8. Workers return results without the human copying them back.
9. Parent automatically detects when the full batch is returned.
10. Parent can reconcile/integrate returns while preserving authority boundaries.
11. Abandon the parent conversation, open another fresh chat, select the same Chat Object, and see the same worker/batch state and exact next frontier.
12. Important design decisions and negative knowledge survive complete conversation loss.

This is the target product. Existing Prometeo infrastructure is substrate; it is not allowed to shrink the target.
