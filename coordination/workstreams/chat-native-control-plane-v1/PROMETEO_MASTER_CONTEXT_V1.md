## 0. Read this first

Prometeo is not a chat helper, not a dashboard, not a worker launcher, and not a collection of prompts. It is a durable cognitive operating system for long-lived projects where conversations/models are disposable execution shells.

The human should not be the scheduler, memory, result courier, context bus, allocator, merger, comparator or recovery mechanism.

Normal target interaction:
- bound parent: `.`
- fresh parent: one stable reincarnation bootstrap
- fresh worker: one identical generic bootstrap
- result transport by human: none
- manual numbered worker assignment: none in the target system

A fresh successor must recover not only facts, but the operating method, critical posture, authority boundaries, current frontier and next safe action.

## 1. Final objective

Prometeo should continuously transform human intent into useful durable progress across multiple project roots with minimal human coordination:

`human goal`
-> Project/Chat Object root
-> Planner/Compiler
-> dependency-aware Opportunity Queue
-> identical fresh workers self-select + atomically claim distinct work
-> STARTED / execute / RETURN / DONE
-> Validator / Steward / Merger
-> durable integration / memory / incidents / evidence
-> Planner recompiles next wave
-> repeat

The loop must survive loss of any parent or worker conversation.

The end state is not "20 busy chats". It is high useful durable progress per human intervention and per coordination cost.

## 3. Human contract

The human must not be required to remember:
- active campaign/batch;
- which workers were launched;
- which workers returned;
- what each worker was assigned;
- what results need integration;
- which project needs attention;
- what prompt belongs to which worker;
- what the next wave should be;
- whether an old chat disappeared.

The system should ask for human action only at a real platform/authority/product boundary.

When the bound parent receives `.` it should:
1. reload durable state;
2. refresh exact worker/claim/return evidence;
3. consume new evidence;
4. derive current frontier;
5. execute useful work immediately;
6. prepare/activate parallel work when safe;
7. persist the changed frontier;
8. reply briefly.

It must not ask the human what to do next when durable state already answers that question.

## 4. Core system roles

### Human
Supplies goals, direction changes, deadlines, acceptance and true authority decisions.

### Root / Chat Object
Durable identity + mission + FOCUS + campaign pointers + current frontier.

### Planner / Compiler
Turns goals, returns, incidents, proposals and blockers into typed dependency-aware work.

### Context Foundry
Provides each worker only the context/evidence required for its mission, with freshness and lineage.

### Worker
Disposable execution shell. Claims one opportunity, works only its scope, returns durably.

### Challenger / Critic
Fresh independent adversarial review where independence matters.

### Validator
Checks contracts, evidence, scope, lineage and test requirements.

### Steward / Merger
Consumes candidate returns, reconciles conflicts, records integration decisions, preserves authority boundaries.

### Product Memory / Canon
Stores distilled reusable operating knowledge and lineage, not transcript dumps.

### Control Plane
Knows what exists, what is READY, claimed, STARTED, RETURNED, DONE, FAILED, STALE, blocked or superseded.

### Live
Optional read-only ambient projection of Control Plane state. Never required for correctness.

## 5. Durable truth laws

- Conversation presence is not durable state.
- Missing claim/run means NOT_CLAIMED / NOT_LAUNCHED.
- STARTED must exist before substantive work.
- Silence is never work or completion evidence.
- RETURNED requires a durable result artifact.
- DONE requires a durable return unless explicitly allowed otherwise.
- A worker disappearance must be recoverable without human archaeology.
- Worker completion does not imply Current, Human Accepted or Served authority.
- Worker returns remain immutable evidence/candidates.
- Integration/consumption is recorded separately.
- Newest-wins is forbidden.
- Rollback does not erase history.
- A fresh successor must prove continuity, not merely retrieve facts.

---

## 6. Parallelism laws

Parallelize aggressively when work is independent.

Do not serialize read-only research merely because shared mutation needs caution.

Workers need independent ownership or isolated append-only scopes.

One worker should not become universal worker merely because it already has context.

Workers may continue after RETURN only through a fresh safe claim or an explicitly authorized bounded follow-up.

The system should prefer:
- useful parallelism;
- information gain;
- unblock value;
- critique where failure would matter;
- low collision risk;
- low human friction.

Do not optimize for occupancy.

- VERIFY
- TEST
- INTEGRATE_ASSIST

Each opportunity needs durable identity, project/root, campaign, priority, mission, dependencies, capability requirements, read/write scope, authority class, claim mode, return contract and provenance.

Workers may create isolated proposals for future work. Proposals are candidates. Planner/Compiler deduplicates, resolves dependencies and promotes useful proposals into the queue.

This is how work generation becomes continuous rather than manually batch-designed by the human.

## 10. Prometeo Live role

Live is not the brain.

Default target display:
- black background;
- no title/noise;
- subtle active light/ring;
- giant counts: working / done / waiting signal / problem;
- one short natural-language current-action line;
- small real progress trace;
- all technical diagnostics and recovery commands behind one toggle.

Live should eventually tell the human the minimum real action, e.g. `Abrí 4 workers`, based on READY queue depth and dependencies.

Progress should be based on durable progress events, not a fake project percentage.

Examples of meaningful events:
- claim / STARTED;
- durable RETURN;
- integration complete;
- dependency cleared;
- incident resolved;
- canary passed;
- authority decision recorded;
- test passed;
- root recovered;
- stale work safely reclaimed;
- human friction removed.

## 18. What exponential progress means here

The desired curve comes from compounding coordination capability, not from opening chats blindly.

A useful generation should improve both:
1. the project output;
2. Prometeo's ability to create/allocate/integrate the next generation.

The compounding loop is:

`better state -> better planning -> more independent work -> better returns -> better integration -> better memory/method -> better next planning`

If each generation only produces more documents without reducing human coordination or increasing autonomous throughput, the curve is not compounding.

Therefore measure progress by:
- human interventions removed;
- distinct useful opportunities completed;
- dependencies cleared;
- returns integrated;
- stale/lost work recovered automatically;
- next waves generated automatically;
- project roots made independently recoverable;
- successful parent/worker reincarnation;
- canaries passed;
- durable capabilities promoted.
