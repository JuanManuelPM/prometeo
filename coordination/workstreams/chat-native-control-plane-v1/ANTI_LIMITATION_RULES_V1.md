# Prometeo Anti-Limitation Rules v1

Status: BINDING META-METHOD RULES
Owner: `chat-object-prometeo-chat-control-main`
Purpose: prevent Prometeo from artificially shrinking the problem, serializing work unnecessarily, or mistaking implementation caution for lack of ambition.

## AL01 — Do not collapse the north star into the current bug
A fresh failure or implementation detail may change one layer, but must not redefine the whole product unless evidence demands it.

Example failure to avoid: bootstrap launch failure -> spending the whole architecture turn only on landing-page syntax.

## AL02 — Separate safety gates from thinking gates
A write-capable canary may gate trust in mutation transport. It must not gate read-only research, archaeology, architecture exploration, adversarial review or planning that can proceed independently.

## AL03 — Parallelize cognition aggressively when scopes are independent
If 10-20 read-only or isolated jobs can advance different dimensions simultaneously, prefer that over forcing one parent chat to reason serially through all dimensions.

## AL04 — Parent is orchestrator, not universal worker
The parent should preserve north star, prepare scopes, integrate and decide. It should not monopolize every investigation merely because it can do them.

## AL05 — Do not overfit to existing architecture
Existing Prometeo infrastructure is substrate/evidence, not a prison. Recover and reuse it when useful, but judge it against the larger objective.

## AL06 — Do not overfit to the latest conversation
Current transcript salience is not architectural importance. Use Big Picture Map, Survival Set, Product Memory and historical archaeology to restore forgotten dimensions.

## AL07 — No detail capture without north-star refresh
Before materially redesigning a detail, re-read/reconstruct the relevant parent objective and adjacent layers. A local improvement must be evaluated for global fit.

## AL08 — Track omitted dimensions explicitly
When a design slice focuses on one area, record which major dimensions remain unexplored. Do not let absence from the current document become accidental rejection.

## AL09 — Use worker diversity, not clones
Parallel scouts should have different roles/questions: architecture, archaeology, adversary, security, campaign/method, context, integration, UX, testing, compaction, product-host integration.

## AL10 — Parallel returns require convergence, not averaging
More workers do not automatically mean better truth. Parent/steward must compare evidence, contradictions and authority, then crystallize a coherent architecture.

## AL11 — Preserve exploratory freedom while isolating writes
Read-only scouts may overlap heavily. Write-capable workers need explicit scope/authority. Do not use write-safety rules to suppress conceptual exploration.

## AL12 — Prefer prepared batches over ad hoc brainstorming
When several large ideas exist, compile them into durable jobs with precise questions/outputs so fresh chats can deepen them independently and returns remain integrable.

## AL13 — Never make the human manage the parallel plan mentally
The Work Board must know what jobs exist, which were launched, what returned and what remains. Human copies tiny launch commands only where platform boundaries require it.

## AL14 — Exploit abundance of chats
Assume up to roughly 20 concurrent/near-concurrent chats is acceptable when the work decomposes well. Optimize for useful parallel coverage, not artificial scarcity.

## AL15 — Do not use 'keep it simple' as unexamined deletion
Simplicity is valuable only after preserving required capability. First map the full problem, then compress without losing invariants.

## AL16 — Distinguish prototype simplification from product deletion
A canary/prototype can intentionally omit capabilities, but omissions must stay marked as temporary and must not silently rewrite the product definition.

## AL17 — Recover historical high-value concepts before inventing replacements
Search earlier Prometeo mechanisms such as Active Method, Written Mind, Context Foundry, Campaign Controller, Planner/Compiler, SESSION_RETURN, Public Wake, Goldens/Vaccines, Prompt OS, Airlock/FABRIC and Steward/Merger before designing new equivalents.

## AL18 — Every major campaign needs a coverage audit
Before declaring architecture 'complete enough', compare it against Big Picture Map + Survival Set and show uncovered layers explicitly.

## AL19 — Use critics to attack hidden conservatism
At least one independent worker should ask: 'What are we artificially assuming is hard/impossible/sequential because of the current implementation rather than the true product constraints?'

## AL20 — Measure actual progress
Prefer metrics/evidence such as recovered mechanisms, decisions eliminated, jobs completed, tests passing, user friction removed, invariants covered and parallel speedup. Avoid mistaking prose volume or planning loops for progress.

## AL21 — Re-plan after batches
A large batch should change the next plan. Do not prepare 18 scouts and then ignore their returns in favor of the pre-batch implementation roadmap.

## AL22 — Product evolution is allowed, silent forgetting is not
Prometeo may reject or replace old ideas, but only through explicit reconciliation with rationale/evidence. 'Not mentioned anymore' is not a valid retirement mechanism.

## Current correction
The present limiting patterns being actively retired are:
1. treating the current Chat Object/worker slice as almost the whole Prometeo product;
2. letting the canary gate unrelated research/architecture work;
3. serializing large design questions through one parent chat;
4. reacting to the latest bug/detail before refreshing the full north star;
5. underusing parallel read-only workers despite abundant available chats;
6. preparing implementation jobs before a complete coverage exploration of method/memory/campaign/context/security/recovery/product-host layers;
7. letting historical high-value systems become footnotes instead of first-class design inputs.
