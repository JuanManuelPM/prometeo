PROMETEO · UNIVERSAL SESSION PREFLIGHT V1
Status: BINDING CONTINUITY GUARD
Fast path: FAST_REINCARNATION_PATH_V1

THIS DOES NOT CREATE A NEW AUTHORITY.
Current Tree, Organism, Work Context, Chat Object, source owners, Design DNA and worker packets keep their existing roles.

CORE LAW
FIRST DURABLE ACTION = CREATE SUCCESSOR SESSION.
READ POINTERS, NOT THE WORLD.
EXPAND ONLY WHEN THE TASK DEMANDS IT.

============================================================
A · FAST REINCARNATION · INTERACTIVE CONTINUATION
============================================================

Use this path when CONTINUE already names a Chat Object and predecessor.

R0 · Parse envelope
Extract chat_object_id, predecessor id/pin, focus if present, predecessor SESSION/JOURNAL refs, preflight/Current Tree ref and predecessor next_action.

R1 · Minimal durable reads
Normal target: about 3–6 reads.
1. this preflight;
2. predecessor SESSION.json;
3. predecessor JOURNAL material head/latest entries needed;
4. named Current Tree or continuity snapshot;
5. one exact plan/source-owner ref already named by SESSION only when needed.

Before READY:
- no broad repository search;
- no general web search;
- no repository clone;
- no Supabase/RPC investigation unless predecessor next_action explicitly requires repairing that source.

R2 · Fresh identity
Create NEW session_id + session_pin. Never reuse predecessor identity.

R3 · Successor publication
Before target-specific archaeology or implementation, publish successor durably.
Preferred one CAS/tree commit:
- successor SESSION.json;
- successor JOURNAL.json;
- successor CONTINUE.txt;
- INDEX.json update;
- predecessor successor_session_id/status update when practical.

If one atomic write is unavailable, use the minimum sequential CAS writes. Do not insert research between them.

R4 · Session Head / bootstrap receipt
Persist enough sanitized pointers for the next shell:
- predecessor_session_id / predecessor_head;
- repo_head_seen;
- current_tree_ref / organism_ref;
- objective_ref / current_plan_ref;
- work_context_refs;
- source_owner_refs;
- preservation_refs when applicable;
- focus_objects / active_project / organism_nodes;
- known_boundaries / known_degraded_sources;
- latest_material_entry;
- next_action;
- request_class;
- bootstrap_status.

Set bootstrap_status=READY once identity, lineage, reopening pointers and exact next_action are durable.
READY does not claim every live dependency is healthy.

R5 · Target-specific expansion
Only after READY:
- resolve the relevant Organism subgraph, not the whole organism;
- read exact target owner/parents/dependencies/related surfaces;
- read objective/plan/baseline;
- read Design DNA/Goldens only if the requested change touches their scope;
- inspect runtime/bytes/tests required by exact next_action;
- implement.

R6 · Normal journal loop
For each material human interaction, update one sanitized journal entry before the final reply.

============================================================
B · DEGRADED OWNER FAST FAIL
============================================================

Live owner works -> use it.
Live owner fails/5xx/times out -> record DEGRADED -> use last-good/cache/GitHub durable owner -> continue when identity/lineage/pointers are sufficient.

Do not turn a failed Current Tree/Organism/Work Context/Supabase read into storage archaeology unless the exact next_action is to repair it.

============================================================
C · REQUEST CLASSIFICATION
============================================================

CONTINUE: advances current plan.
COMPATIBLE_DELTA: improves/adds while preserving objective/baseline.
EXPERIMENT: explores an alternative without replacing CURRENT.
REPLAN: changes objective/order/strategy; preserve what is superseded and why.
DESTRUCTIVE_RESET: removes/rebuilds known-good behavior; obey human intent while preserving rollback/history where technically reasonable.

Human intent is the new intent. Durable history prevents amnesia; it does not veto change.

============================================================
D · ORGANISM TARGET RULE
============================================================

Resolve only the relevant subgraph:
target node, owner, parents, dependencies, related surfaces/capabilities, status and known plan/baseline.

Do not traverse the full Organism unless the task is genuinely global.
Organism informs execution; it never grants mutation authority.

============================================================
E · NEW / ADOPTED INTERACTIVE CHAT
============================================================

NEW CHAT:
- read this preflight + supplied focus/Current Tree pointer;
- create fresh session identity durably before broad discovery;
- reuse an existing Chat Object/Work Context when pointers show one;
- then expand target-specific context.

ADOPT EXISTING CHAT:
- create a fresh durable session first from supplied focus/visible conversation identity;
- then backfill only material milestones supported by visible conversation or durable refs;
- record predecessor only when real evidence names it.

Never publish raw private prompts, private note bodies, credentials, headers or hidden reasoning in the public journal.

============================================================
F · WORKER VARIANT · DISPATCH FIRST
============================================================

Workers use the same continuity principles but not the interactive startup order.

Worker order:
1. create fresh worker identity/beacon required by CURRENT worker prompt;
2. dispatch/claim through CURRENT;
3. if WORK is returned, obey packet authority/scope;
4. before material mutation, read this preflight and only target-specific Current Tree/Organism/objective/baseline context;
5. read Design DNA only when owned work touches material architecture/global behavior;
6. execute and return evidence through existing worker protocol.

A worker must not:
- create an interactive Chat Session as prerequisite to claim;
- traverse all Prometeo before claim;
- choose project/task/priority from Organism;
- use context to expand allowed_paths, tool_policy, authority or done_when.

============================================================
G · SUCCESS BUDGET
============================================================

Normal continuation target:
- 1 continuation envelope;
- ~3–6 durable reads;
- 1 successor publication CAS;
- bootstrap_status=READY;
- then target-specific work.

Fast-path canary verifies fresh identity, correct lineage, durable bootstrap refs, preserved next_action, no human recap, no broad search/clone/Supabase before READY, no invented owner and no private raw prompt publication.
